# 部署模型与设计

本文描述当前实现的部署语义。系统分层与数据位置见 [架构文档](architecture.md)。

## 核心对象

| 对象 | 含义与约束 |
| --- | --- |
| Project | 权限与发布的组织边界 |
| Target | 一个部署目的地，维护当前 Agent ID、generation 和配置。同一目标串行执行 |
| Release | 不可变的受管 Compose 内容；镜像固定到摘要 |
| Target configuration | 固定版本的目标配置，包含密钥版本与服务挂载授权 |
| Deployment snapshot | 固定 Compose、目标配置、密钥和健康等待。外部资源绑定和受管 Compose 维护包含节点身份与代次。强制重建标志也受快照摘要约束 |
| Deployment / Execution | 部署请求及其派发执行身份；重试沿用身份，不因网络重连重新启动 |
| Agent generation | 凭证轮换后的身份代次，隔离旧节点连接和新工作 |
| Node operation | 绑定节点身份、代次、资源标识和操作参数的任务。适用于 Docker 资源维护及外部 Compose 更新 |
| Node display name | 绑定稳定节点 ID 的展示数据，由平台管理员维护。控制台同时展示系统采集的主机名 |
| Recovery epoch | 恢复数据库的隔离标记，将历史执行证据与新派发分开 |

发布支持完整 Compose 输入和管理员预先发布的模板加镜像替换。两种方式经过同一编译与摘要验证；CI 不能通过模板更新修改未授权字段。发布 API 要求调用方提供镜像摘要，主服务不联系镜像仓库解析 tag。

## 幂等与部署权限

部署 API 要求 `Idempotency-Key`。同一凭证重试同一请求返回原部署，不能用同一键悄悄换掉内容。HTTP 接收成功表示请求已落库，最终是否成功需查询部署状态。

部署请求通过权限和快照校验后直接进入队列。派发前重新检查提交者的角色或 CI 凭证有效性。撤销权限后，已受理执行仍可回报结果。

平台管理员、项目管理员、操作员、查看者的权限见 [用户与权限](access.md)。

## 状态与执行互斥

正常路径为 `queued` → `dispatching` → `executing` → `verifying` → `succeeded`。实际事件可根据执行证据走失败、取消或核查分支；这不是要求每次回报都经过全部中间状态。

| 状态类别 | 处理原则 |
| --- | --- |
| `queued` | 尚未派发，可在事务内取消 |
| `dispatching` / `executing` / `verifying` | 可能已触发副作用，保留执行身份与目标槽 |
| `reconciling` / `needs_attention` | 结果不确定，保留证据与锁，等待核查 |
| `succeeded` / `failed` / `canceled` / `abandoned` | 已确认终态，按事务规则释放槽 |
| `abandoned` | 人工处置记录原结果无法确认，不伪装为成功或安全取消 |

Agent 在启动外部命令前提交执行阶段。重启发现已开始但无终态记录的执行时，进入核查，不重新启动同一工作。只有持久化记录证明尚未启动的已受理工作才可继续执行。

## Docker 语义

目标对应稳定的 Compose project。模板的外部卷和网络按名称写入快照，同时固定节点身份与凭证代次。提交和派发都遵循该约束。带外部资源绑定的部署等待派发时，需要先处理部署才能改绑节点；跨节点部署应重新选择当地资源并提交。节点先通过本机 Docker 拉取固定摘要的镜像，并按镜像域名和仓库路径匹配全平台共享的 Registry 凭证。拉取成功后，调用 `up --detach --remove-orphans --no-build --pull never --wait`。更新会移除不再属于项目的服务，保留命名卷。

成功取决于 Compose 等待结果。有健康检查的服务需要健康；没有健康检查时只能确认运行状态，不能宣称应用业务可用。进程超时或终止无法保证 Docker 已撤回操作，因此不确定结果需要核查。

## 节点维护模型

### Moori 受管 Compose

以目标最近一次成功部署的快照作为编辑底稿。预览读取当前目标配置和密钥绑定，校验当前目标节点及空闲状态。提交时在事务中再次检查基线、节点代次、目标状态及预览摘要，同一幂等键可重试。按当前配置重新部署时，将强制重建标记写入新快照。两个操作均创建新部署，并直接进入队列。回滚则复用指定历史部署的快照。

### 外部 Compose

节点管理员可以登记原始 Compose 源文件，平台管理员按登记顺序读取、预览和保存。保存前节点重新核对全部文件的内容版本。无可用源文件时，平台管理员可提供完整项目定义，预览时规范化并计算摘要。执行时检查节点代次和现有项目，在原项目名下应用配置，保留文件未列出的服务。镜像可使用标签，由节点解析并按需拉取。两种方式的边界见 [Compose 支持范围](compose-support.md#外部-compose-项目)。

### 独立容器

节点按原容器完整 ID 读取实际配置，应用允许的配置变更。节点使用 Docker 实际分配的卷名重建匿名卷绑定。卷名和目标路径保持相同时，沿用旧挂载选项，可单独修改读写权限。节点创建候选容器，在停止旧实例前核对实际停止配置与候选容器的健康检查。替换限时三分钟，其中预留最多 25 秒恢复时间。停止配置可无限等待，或停止和健康检查所需时间超出预算时，执行停止前拒绝替换。候选容器启动或健康检查失败时尝试恢复旧实例。恢复或清理的结果不确定时，需要核对 Docker 现场。容器可写层随替换重建。复杂网络和挂载的已知限制见 [Docker 资源管理](docker-management.md#维护-compose-配置和重新部署)。

流水线通过[容器部署 API](integrations.md#gitea-actions-直接部署独立容器)提交带摘要的镜像。CI 令牌可以授权多个目标，每个目标固定绑定节点代次、容器名和镜像仓库；Webhook 也可独立绑定一个容器。节点按名称定位容器，核对当前仓库、容器归属和替换条件。镜像缺失时先拉取固定摘要的镜像，再按已核对的完整容器 ID 执行替换。节点操作队列负责串行执行，并与同节点的 Compose 部署互斥。使用旧摘要可回退镜像，替换沿用此时的容器配置。

## 取消、回滚与恢复

取消先持久化请求，再通知对应执行。尚未启动时可安全取消；已启动时终止对应工作进程，但若 Docker 结果未知仍需保留锁。已经确认的成功不会被迟到的取消请求改写。

回滚创建新的部署，复用历史成功部署的精确快照，并在校验后进入队列。快照包含外部资源绑定时，回滚仍要求原节点和凭证代次。原部署不变，卷和业务数据不参与回滚。已撤销密钥版本不能被回滚重新启用。

数据库恢复使用新文件与新的 recovery epoch。恢复的会话、CI token 和 Agent 凭证失效；先重发凭证、收集原账本盘点并核对现场，再逐目标释放。凭证代次隔离只阻止旧身份通信，不能证明旧机器上的 Docker 已停止。

## 会话与审计

用户会话凭证以哈希保存，节点显示名变更和密码锁定进入平台审计。密码错误按账号累计，连续五次触发十五分钟锁定，主库保存计数和期限。锁定期间不能建立新会话，现有会话仍按原期限和撤销规则处理。平台管理和项目管理的授权分别校验。浏览器可通过 HTTP 直连，也可使用可信网关，详见[用户与权限](access.md)。

## 密钥、诊断和健康

密钥值加密存于主服务数据库，主密钥单独保管。执行快照固定版本与服务授权，Agent 仅可获取自己被授权执行的密钥包。密钥文件在挂载可能存在时保留，离线回收需核查所有容器挂载。

执行结果与诊断输出分离：结果必须持久化确认，日志仅为有预算限制的尽力诊断。主机健康使用当前代次的联系和采样数据；缺失或过期数据不视为健康。

对应操作见 [密钥管理](secrets.md)、[部署运维](deployment-maintenance.md)、[节点监控](observability.md) 和 [验收清单](linux-deployment-acceptance.md)。
