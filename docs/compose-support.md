# Compose 支持范围

Moori 通过本机 Docker 发现已有 Compose 项目，包括在控制台之外创建的项目。发布使用受管的 Compose 子集，由节点上的官方 Compose CLI 执行。

## 在节点新建项目

在本机 Docker 或远程 Agent 的「Compose → 创建 Compose 项目」填写项目名，粘贴一份完整的 YAML 后部署。例如，以下配置会在所选节点启动一个 Web 服务并发布端口 8081。

```yaml
services:
  web:
    image: nginx:alpine
    ports:
      - "8081:80"
```

节点使用项目名运行官方 Docker Compose，先校验配置，再启动服务。镜像可用标签或摘要。节点优先使用已有镜像，缺少时由 Compose 拉取。使用需要认证的私有镜像时，可先在该节点的镜像页通过共享仓库凭证拉取同一标签。配置须能以单份文件独立运行，环境变量填写明确值，镜像提前构建。持久化数据可使用具名卷，绑定挂载请填写目标宿主机上的绝对路径。

从项目详情进入「查看 Compose 源文件」即可打开原始 YAML。编辑后点击「校验并预览」，然后选择「保存到源文件」或「保存并部署」。文件保存在执行节点账本同目录下的 `compose-projects/`，容器默认使用 `/data/compose-projects/`。默认的数据卷即可持久化这些文件。删除项目容器后，原文件保留；用同名项目重新部署时会创建新的源文件目录。远程节点需同步升级至支持新建项目的 Agent。

## CI 和模板的发布内容

发布文档支持顶层 `services` 和可选的项目卷 `volumes`、项目网络 `networks`。服务可声明 `image`、列表形式的 `command`、重启策略 `restart`、`environment`、`labels`、简短语法的 `ports` 和 `volumes`、列表形式的 `networks` 以及 `healthcheck`。环境变量和标签接受映射或显式的 `KEY=value` 列表，编译后保存为映射。镜像须固定到 SHA-256 摘要。未知字段和变量插值会被拒绝。节点在执行前校验不可变的快照。

项目卷和项目网络使用空定义，例如 `volumes: {data: {}}` 和 `networks: {backend: {}}`。服务使用 `data:/var/lib/app`、`data:/var/lib/app:ro` 或 `data:/var/lib/app:rw` 挂载卷，通过 `networks: [backend]` 引用已声明的网络。每类资源最多 64 项，每个服务最多挂载 64 个卷、引用 64 个网络。卷挂载目标必须是唯一的绝对 Linux 路径，经规范化后仍保持原样，且不能是 `/`。卷挂载路径与绑定的 `/run/secrets/NAME` 或其父子路径不能重叠。

普通 CI 发布使用项目自己的卷和网络，支持范围排除宿主机绑定挂载、匿名卷、长格式挂载、自定义驱动和驱动选项。控制台可通过[模板](docker-management.md#compose-模板)声明外部绑定。受管项目维护也接受显式的外部卷和网络声明。受管部署执行前，节点核查外部卷为无驱动选项的本地命名卷，外部网络为用户创建的本地 Bridge 网络。

## 健康检查

`test` 使用 `[CMD, executable, ...]` 或 `[CMD-SHELL, "shell command"]`，最多 64 项且每项最多 4096 字节。`interval`、`timeout`、`start_period` 和 `start_interval` 接受 1 ms 至 30 min 的时长字符串，`start_period` 也允许零。`retries` 可选，范围为 1–100。省略的字段采用 Docker 默认值。发布校验拒绝 `NONE` 和 `disable`。

服务未定义健康检查时，Docker 使用镜像自带的健康检查。镜像也没有健康检查时，Compose 只等待容器进入运行状态。

## 外部 Compose 项目

Compose 列表标明管理方式。通过 CI 或模板发布的项目按部署版本维护。从节点页面新建的项目可直接编辑保存的 YAML。对于外部项目，源文件可读时可以进入编辑器，源文件不可读时可以浏览运行配置和执行允许的单容器操作。

外部项目编辑页可以回填原始 Compose YAML。在运行项目的主服务或 Agent 设置 `MOORI_COMPOSE_SOURCE_ROOT=/srv/compose`。容器化运行时，把宿主机源目录挂载到相同绝对路径。Moori 按项目容器记录的源文件顺序读取授权根目录内的 YAML。

挂载路径不同、源文件标签缺失或项目容器记录不一致时，设置 `MOORI_COMPOSE_SOURCES={"edge":["edge/compose.yaml","edge/compose.override.yaml"]}` 手动登记。清单以实际 Compose 项目名为键，路径相对授权根目录，顺序与部署时的 `-f` 一致。设置清单后以清单为准。只读挂载可以查看原文，保存需要挂载可写且服务用户有写权限。

编辑器按文件编辑，保存时校验全部已登记文件的内容版本。系统使用首个文件所在目录作为 Compose 项目目录。由 Git 管理的源文件写回节点工作目录，Git 提交继续走项目现有流程。

管理员应将授权目录的写权限保留给受信人员。保存前会重读并核对整组版本。主机直接编辑与 Moori 写回应错开进行，因为外部编辑器不使用 Moori 的锁。等待处理的编辑草稿加密暂存，主服务重启后需重新提交。

已登记文件可原样读取。页面的校验和部署只使用已登记的文件组。依赖隐式环境变量、环境文件、附加文件引用或构建的项目，继续在原主机工作流中维护。

平台管理员可从外部项目详情删除该节点上属于项目的容器，所有卷均保留。删除容器按 Docker 的 Compose 项目标签执行，无需读取 YAML。授权源文件可读取时，还可在源文件页面维护配置或选择清理符合条件的项目卷。

## 纳管外部项目

源文件可读且只有一个 Compose 文件的外部项目，可在源文件页执行「评估纳管」：控制台把该文件转换为受管子集并生成模板，随后走标准的模板部署流程。转换完全基于节点快照与已授权的源文件，不访问镜像仓库——镜像按节点快照记录的仓库摘要固定（RepoDigests），受管部署以 `--pull never` 执行，因此纳管不需要任何 registry 凭据。

转换逐服务进行，只保留受管模型可等价执行的配置：

- 可保留：镜像（固定到节点快照中的摘要）、列表或标量 `command`（标量按 Compose 的分词规则拆分）、重启策略、`environment` 与 `labels`（映射或 `KEY=value` 列表）、简短或可转换的长格式 `ports`（host 模式与区间端口除外）、具名卷挂载、已声明网络的引用、可映射的 `healthcheck`。
- 忽略并注明：`container_name`（纳管期间新旧项目并行，必须避免重名）、`depends_on`（不保证启动顺序）、`expose`、网络的自定义设置（别名、静态地址）、`healthcheck` 的 `disable`/`NONE`、继承外部环境或含变量插值的变量值、Compose 内部标签。
- 跳过整个服务并注明：`build`、`env_file`、绑定挂载或匿名卷、`deploy` 资源限制、`network_mode`、`privileged` 等其余受管模型之外的配置项。挂载目标不唯一或含插值的镜像/命令同样跳过。

项目卷和网络一律转为指向现有 Docker 资源的外部声明（`<项目名>_<键>`，或源文件已声明的显式名称），部署时在部署表单中绑定回原名即可复用现有数据；未显式声明网络的服务会共享原项目的默认网络。整个转换的结果在保存前已通过发布编译校验，每个简化都有明确说明，不做静默丢弃。

纳管完成后的收尾：部署模板并核对运行正常，然后回到原项目页删除旧项目。多文件项目（override、include）暂不支持，请先合并为单一文件。

## 受管部署执行

节点通过本机 Docker Engine 拉取固定摘要的镜像，然后在目标的稳定 Compose 项目中执行 `compose up --detach --remove-orphans --no-build --pull never --wait`。更新会移除该项目中已经不属于新发布的服务，保留命名卷数据。部署的健康等待超时与每个服务自身的检查间隔和超时分别计算。受管项目重新部署会根据执行快照追加 `--force-recreate`。
